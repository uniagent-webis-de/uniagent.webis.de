Synopsis

Build retrieval systems (Task 1) and agents (Task 2) to support selected administrative tasks at a university. We are collaborating with administrative staff at the University of Kassel to ensure that the systems work on real data for real information needs and administrative tasks.

  • Submission: [runs via TIRA, notebook papers]

    • The sub-tasks are independent: entering one does not require the other. A submission to Task 2 does not require a submission to Task 1.

    Task

    In its most generic form, the class of tasks we study can be described as follows:

    Given a digital environment and a problem or task (the objective) that is typically tackled by a person acting in the environment, develop an intelligent agent that achieves the objective on the person's behalf by planning and executing the necessary steps in accordance with the environment's codes of conduct.

    Topic areas

    The first edition focuses on four administrative task areas:

    • Business travel: travel permit requests, compliance checking (e.g., hotel rate limits, private extensions), and reimbursement processing. Topics are derived from labeled mail exchanges between administrative staff and university staff.
    • Privately advanced costs: reimbursement of out-of-pocket expenses paid by university staff.
    • Internal procurement: identification, selection, and ordering of goods through the university's procurement system.
    • Administration of student employees: the paperwork around employing and administering student assistants.

    Tasks

    We have two Tasks

    1. Task 1 (Retrieval): Given a query that is intended to help solving an administrative task at a university, retrieve relevant documents for this query from the public website of the University, from the private intranet of the university, and state laws and regulations. Output a standard TREC-style run file.
    2. Task 2 (Solving): Build a working agent that solves complete administrative university tasks in a batch. For each task in the batch, the agent has all forms and administrative documents of the user as input and should output the administrative solution to the task. The agent should, additionally to the solution of a task, also write a log of actions, tool use, etc., so that administrative staff can verify why the agent arrived at a given solution.

    Data & Tools

    The environment comprises a document collection, a set of topics, and a hosted language model.

    Document collection

    The document collection is a crawl of the University of Kassel's web pages and other sources, compiled with the OpenWebSearch.eu project. We mount the crawl into your container as pre-processed documents with the main content already extracted, so every team starts from the same collection. We prescribe no index: indexing the collection from scratch takes under a minute at this scale, so you bring your own retrieval pipeline or search the documents directly, and keep full control over index and ranking.

    The mounted collection is plain text, so no parsing is needed on your side. The underlying material is largely German; teams may translate as needed.

    Topics

    We compile a collection of topics across the four task areas above, drawing on the hands-on expertise of administrative staff trained in the University of Kassel's “AI FrAIdays” seminar series. The topics are fully anonymized. Each topic consists of a user query (with any attached documents), an expected output following the prescribed process, and annotations for query type, complexity, and rule area.

    The case documents attached to a topic — forms, receipts, invoices, and correspondence — are text-based PDFs, and your agent has to parse them. This is unlike the document collection above, which arrives already extracted. Image-only documents such as scans and photos are excluded, so no OCR or vision component is needed.

    A small demo dataset (“business-trip-spot-check”) on TIRA shows the topic format and lets you check that your submission runs. It is deliberately too small to train on or to measure agent quality. A larger public development dataset adds synthetic cases with reference solutions to develop against. For the Retrieval sub-task we also provide spot-check datasets in German and English, built from our public crawl, with queries synthesized against a target document and first-stage retrieval baselines; as queries and judgments are both synthetic, these confirm that a system works rather than evaluate how well it works.

    The evaluation topics stay inside TIRA and are not released. You submit your agent as code (a Docker image), and TIRA runs it against the data. You receive the evaluation measures, never the evaluation topics or the gold references. See TIRA’s participation guide for details.

    Execution environment

    Submissions run in a sandbox without outbound network access, so external LLM APIs cannot be called. We host a small set of open-weight models, among them gpt-oss-20b, and expose them through a REST API inside the environment. Packaging your own weights is not permitted, so that results reflect the agent design rather than available compute.

    Each run gets 4 CPU cores and 20 GB of RAM, plus access to the hosted model. The time limit is 5 minutes per case and 4 hours for a complete run. We supply the environment, and you supply the tools: your agent brings whatever tools it needs inside your image.

    The cases are fully anonymized. No personally identifiable information (names, mail addresses, phone numbers) of university staff is contained in the collection.

    Output Format

    Input: a task description (a user request, optionally with attached documents). Output depends on the chosen sub-task and follows prescribed formats: for Retrieval, the retrieved documents in the TREC run format; for Solving, the synthesized solution together with action logs in a common protocol format, the retrieved documents, and reasoning tokens as plain text. Validation tools are provided.

    Submission

    Submissions are handled via TIRA, the shared task’s reproducibility platform. You submit your agent as code (a Docker image) and may submit and run as often as you like during development. For the official evaluation, each team submits up to five runs, which you select yourself before any results are known. Validation tools check submission format and completeness.

    Submit a client-side cache with every official run, recording the model and tool calls that produced it: prompts, responses, and retrieved sources, verbatim. This is more than the reasoning-token log. We rank runs by success, and we also check whether that success was reached for the right reasons, which needs the full trace. Without a cache, a run cannot be told apart from a zero-shot prediction. This follows the caching approach used by the TREC AutoJudge track.

    The full participation process is described on the rendition overview.

    Evaluation

    We combine manual and automatic evaluation. Each sub-task is scored on the same gold topics, with criteria matched to its required output:

    • (1) Retrieval. Retrieved documents are judged against the set of sources needed to make progress on the task, using recall-oriented IR measures (Recall@k, MAP, nDCG). Recall is the primary measure.
    • (2) Solving. The synthesized solution is scored on task success, a binary criterion. A run succeeds if it produces the minimal solution a peer would accept, such as a reimbursement application with valid receipts. Non-successful runs are then ranked more finely by the number and severity of their errors: rule violations, missing receipts, or incorrect form fields. The agent behavior log additionally yields tool-use accuracy (precision and recall of tool calls) and retrieval quality. A qualitative audit finally verifies that the solution was reached for the right reasons.

    Across all sub-tasks we also report efficiency measures: manual task-completion time (a trained-human baseline), runtime, and environmental impact, for which we investigate the TIREx tracker. Judges compare solutions against expert reference solutions, ideally via a diff visualization; trained laypeople suffice for most topics, with regulatory edge cases referred to domain experts. Automatic LLM-as-judge measures will be validated against the human reference-based judgments on a sample before being used to rank systems. The organizers carry out the necessary judgments and assessments.

    Related Work

    This task builds on and complements prior community evaluations:

    • TREC Enterprise tracks (2005 to 2008). We revisit the enterprise setting with a more holistic aim: rather than retrieving information for a query, we automate achieving the objective, of which retrieval is a sub-task.
    • TREC Million LLM track (2025 to 2026). Retrieving expert LLMs for specific tasks complements ours, as an agent may consult such an expert while executing its plan.
    • TREC RAG track (2024 to 2026). A RAG response is a synthesized solution integrating retrieval, but does not include tool calling or richer environment interactions.
    • TREC AutoJudge track (2026) and the CLEF evaluation labs (e.g., Touché, LongEval), with which integration and shared expertise are foreseen.
